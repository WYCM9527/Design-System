# 中后台统一规范零基础上手教程

如果你啥都不想看，先在「2. 选颜色」挑个颜色，再复制「3. 首次接入」里的那段提示词发给 AI，它会自动检查、安装和部署，你只需要判断即可。

Morganite 是一套后台界面规范，统一按钮、表格、颜色和布局：沿用 Ant Design Pro 的交互结构和纯灰骨架，支持亮 / 暗两种主题。品牌色可以选：默认玫瑰金，另有蓝、紫、青、绿和黄晶黄；选哪个，按钮、表格、表单的结构和规则都一样，只是颜色不同。你描述需求，AI 按规范接入和做页面；数据、权限和业务功能仍要按项目需要实现。

可以先看一眼[在线效果预览](https://wycm9527.github.io/Design-System/morganite/previews/rose-gold-admin/)：工作台、交易记录、新建交易、交易详情、系统设置、组件走查、登录、空状态 8 个页面，顶栏右侧切亮 / 暗，右下角「规范调节」换颜色，接入后的页面应该和它一致。第一次使用，按第一部分的五步做；升级、换颜色、团队协作等内容遇到时再看第二部分。完整参考（原理、命令、维护者事项）在 [GUIDE.md](GUIDE.md)，Morganite 自己的说明在 [Morganite README](../morganite/README.md)。

**注意：代码框里的内容是发给 AI 的提示词。** 只替换 `【】` 里的内容；技术信息不知道就写"不确定"，让 AI 检查。每次复制当前需要的一段，不必一次贴完全文。

# 一、首次使用：五步

## 1. 打开项目和 AI

- **新项目：** 新建一个空文件夹，例如 `supplier-admin`，用编码工具打开它。这个文件夹就是项目位置。
- **已有项目：** 打开原项目文件夹，准备好说明哪些页面要改、哪些要保留。
- **让 AI 能动手：** Cursor 把聊天面板切到 **Agent** 模式（Ask 模式只会回答，不会改文件）；Claude Code、Codex 默认就能。中途要权限时一般点 `Run` 即可。

首次准备的时间取决于电脑环境和网络。你主要判断需求、改动范围和页面效果；遇到需要选择的事情，让 AI 先解释影响、给出推荐，不必逐行审代码。

---

## 2. 选颜色

打开[效果预览的颜色面板](https://wycm9527.github.io/Design-System/morganite/previews/rose-gold-admin/?panel=open)，在「颜色」页点一个颜色，整站立刻换成它，亮 / 暗都切过去看看。从「官方」里选一个：

| 颜色 | 说明 |
| --- | --- |
| 玫瑰金 | 默认颜色，拿不准就用它 |
| 蓝、紫、青、绿 | 主按钮是品牌色底白字，链接、选中、焦点用同色系 |
| 黄晶黄 | 原来黄晶规范的黄：主按钮是黄底黑字；黄字在白底上看不清，链接、选中、焦点用黑色 |

团队有统一要求就用团队的。选了以后随时能换，一句话的事，页面不用重做（见第二部分「换颜色」）。「仅预览」里的颜色（橙、红等）只能在预览里试，没有经过整套检查，项目要用先提案。

## 3. 首次接入：让 AI 检查并安装

每个项目首次接入时使用。已经接入的项目直接到 [第 4 步](#4-实际怎么应用)；换电脑或新队友接手，见 [团队协作](#团队协作队友接手)。

先想好四个填空。例如：

| 填空 | 新项目示例 | 旧项目示例 |
| --- | --- | --- |
| 颜色 | 玫瑰金 | 蓝 |
| 项目用途 | 管理供应商资料 | 已有采购后台 |
| 本次范围 | 新建，先做供应商列表 | 只调整供应商列表和详情页 |
| 保留内容 | 无 | 审批、报表及原有业务逻辑 |

新项目默认用 Vue 3 + Element Plus；想用 React + shadcn/ui，在"本次范围"里写上即可。

这段首次提示词较长：前四行是你的需求，其余是让 AI 检查环境、下载安装和自检的固定内容，不用理会。后面日常修改用短提示词即可。

```text
请帮当前打开的项目接入 Morganite，颜色用【玫瑰金 / 蓝 / 紫 / 青 / 绿 / 黄晶黄】。
用途：【项目用途】
本次范围：【新建项目，或要调整的页面】
需要保留：【不改的内容，没有就填"无"】

来源：https://github.com/WYCM9527/Design-System
先只读识别项目目录、现有规则、技术和接入状态，简要说明路线；不确定的业务范围再问我。已完成的步骤不要重复。

准备与获取流程：
1. 按实际系统、终端检查 Node.js（至少 22，并满足项目依赖要求）、git 和 Chrome；缺少或过旧时说明影响并按当前工具权限补齐，需要我操作时给出步骤。后续命令使用实际路径，不假定我在 Cursor 或某一种系统里。
2. 旧项目在首次写入前，检查未提交改动，说明并确认本次存档内容，保存接入前的本机 git 存档点；不要把接入改动混进这个存档。
3. 从上述仓库获取源码到独立临时目录，读取根目录的 design-system-adopter/SKILL.md 及对应流程。将 adopter 安装到项目内的 skill 目录（Cursor 是 .cursor/skills/design-system-adopter，Claude Code 是 .claude/skills/），随项目提交给队友共用；只有当前工具不支持项目级 skill 时才装到全局目录并注明。记录实际路径，后续调用统一使用该路径，并明确目标项目。读不到流程时报告原因，不猜步骤。

按项目类型接入：
4. 新项目使用当前空目录，不另套同名文件夹；默认 Vue 3 + Element Plus（也支持 React + shadcn/ui），有团队要求则沿用。先建立并验证可启动的应用，再装 Morganite，不能只凭 package.json 判断已有完整应用。已有项目沿用原技术，仅做指定范围的第一期换肤，完成后暂停。
5. Node 项目按流程安装 @wycm9527/morganite、开发依赖 @wycm9527/citrine-tools（验收工具）和种子声明的构建依赖，检查 steward 是否可用且满足最低版本。接入时按流程带上我选的颜色。npm 获取失败先诊断（国内可换镜像 https://registry.npmmirror.com），也可使用该仓库的种子目录和官方 Releases；不把项目外的临时路径写进依赖。
6. 非 Node 项目走纯 CSS 导出流程，导出时带上我选的颜色（官方 Releases 里的 morganite-css 包是玫瑰金的，选玫瑰金可直接用），保留原运行方式；导出的几个 CSS 文件放在同一目录（base.css 会引入同目录的数字字体 fonts.css）。本地导出和验收仍需工具。使用已取得的验收脚本或明确安装 @wycm9527/citrine-tools，先建有实际页面的 accept.config.mjs，再对运行中的服务检查。端口由你确认。
7. 只改部分页面时，先判断能否隔离并记录保留页面的原始状态；核对实际使用者的浏览器兼容性。若组件库缺少适配，说明哪些效果做不到，等我选择，不冒充已完整接入。

按规范接好样式、亮暗主题和适用的手机交互，登记真实页面及必要状态并验证。页面效果以在线效果预览为准（切到我选的颜色看）：https://wycm9527.github.io/Design-System/morganite/previews/rose-gold-admin/ ；它只作视觉参考，预览自己的样式文件不拷进项目，用规范的配方实现。新项目先完成最小示例页面；不要在空页面清单上宣告验收通过。不手改上游快照，不靠删检查或放宽规则制造通过。
技术做法可按环境调整，正常故障可在原范围内诊断修复；需要扩大范围或改变需求时说明并给建议。阶段开始时简要汇报，必要的确认集中说明影响。
结束时给我：实际项目和工具路径、使用版本和颜色、存档点、预览网址、已做内容，以及通过/未通过/跳过/未执行的检查结果。留下当前阶段可用的项目规则（AGENTS.md），写清已接入和待迁移范围。把接入方式、版本、工具定位方式、启动方法及完成/待办保存到项目说明文件，注明记录位置；机器专属路径注明换电脑后需重新检测。
```

**这一步完成后：**

- 你应能打开 AI 给的网址，看到**新项目的示例页或旧项目的改后页面**，按钮、表格、卡片这类组件的样子和在线效果预览（切到同一个颜色）一致。
- 检查报告里**有未通过或未执行的内容**，下一步先处理；属于后续迁移的问题列入清单，由你决定是否继续。
- 旧项目的 git 提交是保存在本机的存档，不等于上传到网上。如果项目有 GitHub 仓库，可以让 AI 把这个存档点也推上去，防本机丢失。之后想恢复时，让 AI 先说明恢复范围，保留你之后新增的业务改动。
- 项目托管在 GitHub 的团队，建议接着做 [验收进 CI](#验收进-ci适用于-github-项目)，一次就好。

## 4. 实际怎么应用

以下提示词用于已经接入 Morganite 的项目，新会话也可以用。选与当前需求匹配的一段。

#### → 当要新增一个页面时

例如页面填"供应商列表"；功能填"按名称、状态筛选，查看详情、新建和编辑"。需要沿用某个页面效果时，补充页面名称或参考图即可；也可以直接指效果预览里的页面，例如"照效果预览的交易记录页"。

```text
在当前已接入 Morganite 的项目中做页面。
页面：【页面名称】
功能：【需要的功能】

先读项目规则、接入记录和实际安装的 design-system-adopter 对应流程；找不到时说明缺什么。非 Node 项目沿用纯 CSS 和运行中服务的检查方式，不强套 Node 构建或工作副本命令。
沿用现有技术和规范：颜色、间距、字号只用规范变量，不写具体数值；页面骨架用现成配方；缺配方先说明，不在页面上补样式。布局、配方组合与实现方式由你结合项目决定。效果预览里有同类页面时，以它为视觉参考、用配方实现；预览里有而配方没有的样式先告诉我，不照着预览另写一套。数据来源先查现有项目；没有业务接口时使用明确标注的演示数据，并说明哪些功能尚未接入。
缺少规范支持时先查已有方案；确实做不到的部分说明影响并给建议，继续不受影响的工作。
完成后更新验收清单并检查，启动预览给我网址，说明已完成、未完成和检查覆盖范围，不把跳过当通过。
```

#### → 当只改一处时

修改文案、增加筛选项、调整某个操作时，用这一段（现在的 AI 一般会自动按规范来做，这段只是再强调一次）：

```text
调整当前项目的【页面或位置】：把【现状】改为【期望效果】。
先读项目规则，沿用 Morganite 和现有实现，只改与需求相关的部分；颜色、间距、字号只用规范变量。技术做法自行判断；若需改变其他页面的行为或修改共享规范，先说明影响。
完成后给我预览，并检查受影响的功能与样式，说明未完成项。
```

## 5. 打开页面，确认是否完成

先用浏览器打开 AI 给的预览网址，再做四件事：

1. **试主要操作。** 例如筛选、新建、编辑；刷新后确认数据是否按预期保留。演示功能和真实功能要分清。
2. **看不同状态。** 试亮暗切换、缩小窗口、打开手机菜单，查看表格和弹窗是否可用。规范有现成方案，仍需要 AI 接好交互。
3. **和效果预览对照。** 打开在线效果预览里的同类页面（如交易记录、新建交易），切到项目的颜色，对比按钮、表格、卡片和数字的样子。数据大字（统计卡、KPI）是 D-DIN 窄体数字；电脑没装 D-DIN-PRO 时会用规范自带的 D-DIN，看起来略粗一点，属正常。
4. **看检查范围。** AI 应列出实际检查过的页面与状态，说明遗漏和不适用项。

**"通过"只说明本次实际运行的界面检查没有发现相应问题。** "跳过"和"未执行"要有原因，不能算通过；功能是否正确、能否上线，还需项目本身的功能检查和发布流程。

如果 AI 只说"完成了"，可以补发：

```text
请核对当前项目的实际完成情况：
给我可打开的预览网址、实际检查过的页面和状态，以及通过、未通过、跳过、未执行各项的结果与原因。
同时说明哪些功能使用演示数据、刷新后是否保留，并给我几个可亲手操作的检查步骤。不要只根据命令正常结束判断完成。
```

检查报告有"未通过"时，把那几行粘给 AI：

```text
验收没过，结果如下：
【粘贴 AI 报出的未通过项】
先归因到层：页面自己写错的现场修；属于组件库默认样式或规范层的问题，不要用 !important 压过去，整理成提案告诉我。修完重跑验收，把前后结果对照给我。
```

# 二、按需使用：特殊项目与后续维护

### 只改部分页面，或项目里有多个子系统

仍使用第 3 步，在"本次范围"和"保留内容"写清页面名称即可；不必先判断是不是 Node、Flask 或其他技术。

| 你的情况 | 需要 AI 说明的事情 |
| --- | --- |
| 一个目录里有多个应用 | 实际改哪个应用，依赖和样式是否相互影响 |
| 同一个应用只换部分页面 | 隔离方式、浏览器要求、改前改后的对比范围；同一屏混用新旧组件不属于范围根方案的支持场景 |
| Flask、Django、PHP 或静态模板 | 网站可消费导出的 CSS（选玫瑰金也可直接用官方 Releases 里的 morganite-css 包）；本地导出与自动检查仍需相应工具和页面清单 |
| 其他组件库 | 当前版本提供 Element Plus、shadcn/ui 适配（另有 ECharts 图表配色）；缺少适配时先说明局限，让维护者评估 |
| 项目设了内容安全策略（CSP） | 要允许 `font-src data:`，否则数据大字的数字字体会退回系统字体 |

保护旧页面，应比较它原来的外观和功能。一张改后截图或"变成组件库默认样式"，都不能证明它没有受影响。

### 旧项目：第一期看过了，继续改剩余部分

接着第一期结果使用。新会话先让 AI 找到此前的范围与清单，找不到时补给它，不能仅凭一句"继续"猜测。

```text
继续当前项目的 Morganite 迁移。先读取规则和上一阶段记录，核对已完成内容、接入前存档及待处理清单。
本次继续处理：【页面或事项】。
按实际安装的 adopter 旧项目流程分批处理，保留已确认的不改范围。需要我判断的取舍整理成一份清单，解释影响并给推荐；每批验证后汇报，不自行扩大范围。
```

### 换颜色

已接入的项目想换品牌色，先在[颜色面板](https://wycm9527.github.io/Design-System/morganite/previews/rose-gold-admin/?panel=open)里看好，再发：

```text
把当前项目的颜色换成【颜色】。先读项目规则和实际安装的 adopter 换色流程，这次只预览：告诉我会变的地方，不改文件。
我确认后再换；换完重新构建、跑验收，给我预览网址和检查结果。
```

换颜色只换品牌色，以及跟着它走的链接、选中、焦点这些颜色，结构和规则不变；页面里只用了规范变量的，页面代码一行不用改。以后升级规范，颜色会自动保留。想要的颜色不在官方名单里（包括面板「仅预览」里的），不要让 AI 直接改色值，按下面「现有规范满足不了需求」提案。

### 验收进 CI（适用于 GitHub 项目）

接入完成后，规则只是被 AI"看见"——它改完页面是否记得跑验收，取决于它听不听话。把验收放进 CI，每次提交 / 合并请求自动跑一遍，不合格的改动进不了主分支。这是唯一不依赖 AI 自觉的保险，做一次就行：

```text
把设计系统验收接进 CI：按实际安装的 adopter 用 ds.mjs ci --dry-run 把要生成的工作流给我看，用大白话说明它在什么时候跑、检查什么；我确认后写入 .github/workflows/ 并提交。项目还没有验收清单（accept.config.mjs）就先建。
```

之后每个 Pull Request 页面会多一个叫 **Design System** 的检查项：绿的合格；红的点进去看哪项没过，把失败信息粘给 AI（第 5 步的"验收没过"提示词）。项目在 GitLab 等平台的，让 AI 照工作流里的步骤改写成你们平台的格式。

### 规范有新版本时

先查看变化，再决定是否升级。项目不会因为仓库发布新版就自动完成更新。Morganite 的版本发布在仓库的 [Releases](https://github.com/WYCM9527/Design-System/releases?q=morganite&expanded=true)（tag 以 `morganite-v` 开头），每版改了什么见 [CHANGELOG](../morganite/seeds/morganite/CHANGELOG.md)。

```text
检查当前项目的 Morganite 版本和可用更新。先读项目规则及实际安装的 adopter 更新流程，识别是普通接入、局部范围样式还是纯 CSS 导出。
这次只预览：不修改项目文件或依赖，不执行实际升级、恢复或 npm update。说明目标版本、页面可能的变化、本地改动和冲突，并给出建议；纯 CSS 项目比较导出清单与新版来源，不强套工作副本命令。
```

看完预览后，在同一会话中发送：

```text
按刚才预览并确认的目标版本升级；若目标版本、改动范围或本地状态变了，先重新预览。
保留升级前存档。有冲突时汇总本地与上游的区别、影响和推荐处理，等我选择，不直接覆盖本地改动。
按接入方式同步实际使用的产物：普通 Node 项目同步包与工作副本，构建 token、运行 guard；使用范围样式的，构建 token 后再次运行 ds.mjs scope；纯 CSS 项目从已确认的新来源重新 export。
随后按项目需要重新构建应用、运行实际页面检查，给我预览、变化说明和未完成项。
```

有些配置可以自动合并；规则文档等文件两边都改过，即使改在不同位置，也可能需要选择。判断时看对页面的影响，不必自己研究合并算法。换过颜色的项目升级后仍是原来的颜色。

### 团队协作：队友接手

项目规则、规范文件（包括 Morganite 的快照 `design-systems/morganite/`）、skill 和依赖清单随项目一起提交，队友 clone 后 `npm install` 就有；仍需可用的基础环境（Node ≥ 22、Chrome）。队友打开项目后可以发送：

```text
我要接手当前已接入 Morganite 的项目。先读项目规则、接入记录和依赖清单，定位实际的 adopter 与 steward，检查所需版本和本机环境。
缺少什么先说明，再按项目记录及官方来源补齐；不要重新初始化设计系统或迁移已有页面。完成后启动预览，告诉我当前版本、颜色、检查范围和后续做页面的入口。
```

### 现有规范满足不了需求

先让 AI 看能否组合已有方案。确实缺能力时，再提案；不要把"我想这样做"直接认定成合法例外，也不要手改上游快照。

```text
我希望【期望效果或功能】。先读当前项目的 Morganite 规则，判断已有方案能否组合实现。
能实现就说明并按本次需求处理；不能时，解释缺口和合规替代。替代会改变效果或功能时让我选择，不受影响的工作继续。
确属本项目的合法例外（如欢迎横幅用了品牌色面），按规范登记进验收配置的允许清单并写明理由；需要改规范时，用实际 adopter 的提案功能生成包含场景、期望效果和证据的草稿及预填 issue 链接，交给我，不自动提交。
```

品牌色能出现在哪些位置，Morganite 已经规定好了（主按钮、侧栏当前项、登录页品牌区、优惠券券面等，见 [DESIGN.md](../morganite/seeds/morganite/design-system/DESIGN.md) 的「验收基线」），换了颜色也一样，这些位置不算例外，不用再登记；欢迎横幅这类规范允许、但没有现成配方的位置，才需要项目自己登记。想加一个官方名单外的颜色，也走这里的提案。

生成链接不等于已经反馈。通常需要登录 GitHub，打开草稿链接、检查内容再提交；随后可在 [Issues](https://github.com/WYCM9527/Design-System/issues) 查看回复。公司有指定维护者时，也可以把草稿直接交给对方。

## 遇到这些词，再来看

| 词 | 在这里是什么意思 |
| --- | --- |
| skill / adopter | 给 AI 用的接入说明和工具，告诉它如何安装、做页面、换颜色和升级 |
| token / 配方 | 命名好的样式值与现成页面结构，AI 应按规范使用 |
| 颜色 | 可以换的品牌色。一套结构配多种颜色，每个项目选一种，记在项目的接入记录里；换颜色由 adopter 一条命令完成，结构不受影响 |
| 桥接 | 让现有组件库（Element Plus、shadcn/ui）呈现 Morganite 外观的适配层 |
| 效果预览 | Morganite 自带的一组示例页面，在线可看，能切亮暗、换颜色；接入后的页面以它为视觉基准，但它自己的样式不进项目 |
| steward / guard | 管理和检查规范的工具；guard 的 `current` 表示相应构建一致性状态，不代表业务功能通过 |
| 快照 / 工作副本 | 上游基线与项目使用的副本；Morganite 的快照在项目的 `design-systems/morganite/`，不手改，项目差异按规范管理 |
| 验收 | 自动检查页面是否符合规范的工具，结果只有通过 / 未通过 / 跳过 / 未执行 |
